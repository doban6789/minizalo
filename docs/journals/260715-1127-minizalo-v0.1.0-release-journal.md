# MiniZalo v0.1.0 — First Public Release

**Date**: 2026-07-15 11:27
**Severity**: Medium
**Component**: Electron app (P5), packaging/CI (P7), GitHub release
**Status**: Resolved

## What Happened

Shipped MiniZalo v0.1.0, the first public release. MiniZalo is an Electron desktop
tool wrapping the unofficial `zca-js` Zalo API to run up to 6 personal accounts
behind a local REST/WS/webhook/CLI gateway for AI agents and n8n. Monorepo: `core`
(headless Fastify+SQLite+zca-js), `cli` (`@minizalo/cli` thin client), root Electron
app (main/preload/renderer). Architecture "PA B": the headless core runs *inside*
the Electron main process because credential encryption needs `safeStorage`, which
only exists in Electron's main process — UI and CLI are just loopback REST/WS
clients behind a static API key.

This session resumed mid-P5 after a context compaction, finished the Electron UI,
built P7 packaging (electron-builder, GitHub Actions 3-OS release matrix, README,
LICENSE, architecture/deployment docs), created the public repo
`vuongnguyenbinh/minizalo`, opened and merged PR #1, and tagged `v0.1.0`. The tagged
build then surfaced three real CI/packaging bugs that only show up when you
actually run the release pipeline for real — not in local dev.

## The Brutal Truth

Everything looked green in the sandbox — typecheck clean, 23/23 tests, electron-vite
compiled main/preload/renderer — and it still broke three separate ways the moment
it hit the real CI/release pipeline. That's the sandbox's fault as much as ours: it
can't run a GUI, can't download the Electron binary, can't do a live Zalo login, so
"passes in sandbox" was never going to mean "release works." The annoying part is
each bug was invisible until the exact CI job that exercises it ran — no amount of
local `npm test` would have caught the ABI mismatch, the deb metadata gap, or the
silent no-op publish. Also not proud that the three fixes went straight to `main`
without PRs, because the release was already tagged and blocking on it — expedience
over process, consciously chosen, but it's debt.

## Technical Details

- **(a) better-sqlite3 ABI mismatch**: root `postinstall` runs
  `electron-builder install-app-deps`, which rebuilds `better-sqlite3` for
  Electron's Node ABI (132). The CI `check` job runs tests under plain Node (ABI
  137) → native module load fails under Node's ABI. Fix: `npm rebuild
  better-sqlite3` inside the `check` job before running tests
  (`fdbb01f fix(ci): rebuild better-sqlite3 for Node before tests`). Lesson: any
  project with a native module in an Electron app has *two* ABIs to satisfy —
  Electron ABI for the packaged app, Node ABI for anything run via plain `node`/CI
  test runner. Never assume one rebuild covers both.
- **(b) deb packaging failure**: electron-builder refused the `deb` target with
  `Please specify author 'email'`. Fix: set `linux.maintainer` to a GitHub noreply
  address, not a personal email, to avoid leaking PII into a public package
  artifact; also set `package.json` author name
  (`5b1ea0f fix(build): set deb maintainer and package author`).
- **(c) release jobs "succeeded" but published nothing**: `electron-builder.yml`
  had `publish: null`, which fully disables the publish provider — so
  `electron-builder --publish always` in CI ran, exited 0, and silently published
  to nowhere. Fix: explicit `publish: { provider: github, releaseType: release }`,
  which also avoids electron-builder's default behavior of creating a draft
  release instead of a public one (`415d093`, `9efcaaf`). Lesson: `publish: null`
  is a real, valid electron-builder config that looks like a no-op default but
  actually suppresses the entire publish step — a false-green CI run is worse than
  a red one because nobody double-checks a passing job.

## What We Tried

Ran full local verification before tagging (typecheck across core/cli/electron,
23/23 tests, electron-vite compile) and trusted it as a release gate. It wasn't
enough — none of these three failure modes are exercised by local typecheck/test/
compile; they only fire inside the actual GitHub Actions `check` job (Node-ABI
mismatch), the actual `deb` packaging step, or the actual `--publish always`
invocation. Each was fixed reactively after the tagged pipeline failed, then
`v0.1.0` was re-pointed to the fixed commit with user approval rather than cutting
`v0.1.1` for what were pure CI/build-config fixes with no app code changes.

## Root Cause Analysis

The sandbox environment this work was verified in structurally cannot run
the parts of the pipeline that broke: no GUI, no Electron binary download, no
real `deb`/`--publish` execution. Local "all green" created false confidence
that the release would just work. Root cause isn't a single bug, it's a gap
between "local verification surface" and "actual release surface" — the fixes
came from watching the real CI run, not from foresight.

## Lessons Learned

- Native modules (better-sqlite3) in an Electron app: rebuild for Node ABI
  explicitly in any CI job that runs tests under plain Node, separate from the
  Electron-ABI rebuild that `electron-builder install-app-deps` does.
- `publish: null` in electron-builder config is a silent kill switch, not a
  default no-op — audit publish config explicitly before trusting a green
  release job.
- Never put a personal email in a public package's Linux maintainer field —
  use a GitHub noreply address.
- Local typecheck/test/compile passing is not a release gate for anything
  involving actual OS packaging or actual publish steps — those only get
  validated by running the real pipeline, which by definition can't happen
  before the first tag.
- CI/packaging emergency fixes landed directly on `main` without PR review
  because the release was already tagged and blocking — accepted debt, not an
  oversight, but flag it so it doesn't become the default pattern for future
  fixes.
