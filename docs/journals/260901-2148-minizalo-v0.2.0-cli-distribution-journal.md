# MiniZalo v0.2.0 — CLI for AI Agents + npm-Account-Free Distribution

**Date**: 2026-09-01 21:48
**Severity**: Medium
**Component**: CLI (`minizalo-cli`), core scenarios repo/routes, CI release pipeline
**Status**: Resolved

## What Happened

Shipped v0.2.0. Two themes: (1) close the CLI gap so AI agents can fully read/write
the scenarios knowledge base and message history without touching SQLite directly,
and (2) let anyone install the CLI globally without owning an npm account/scope.

Added 3 CLI verbs: `minizalo messages` (GET /messages, read stored history),
`minizalo scenario update`, `minizalo scenario delete` (PUT/DELETE /scenarios/:id).
Wrote three docs targeting different readers: `docs/huong-dan-su-dung.md` (Vietnamese,
end users + agents), `AGENTS.md` (root, AI-agent front door), `docs/ai-agent-integration.md`
(English playbook). Renamed packages `@minizalo/core`→`minizalo-core`,
`@minizalo/cli`→`minizalo-cli` (scope never existed on npm — 404 on lookup). Decided
against publishing to npm registry at all; distribution is now a tarball attached to
the GitHub Release via a new `cli-tarball` CI job. Tagged `v0.2.0`, full 4-job pipeline
green, verified `releases/latest/download/minizalo-cli.tgz` resolves and installs.

## The Brutal Truth

The PUT /scenarios/:id bug is the kind of thing that should never survive to a
demo: change only `trangThai` on a scenario, get back a scenario with `ten: ''`.
Silent data loss on a *partial* update, the exact operation an AI agent scripting
against this API would call constantly. Caught it "en route" while building the
verb, not by a deliberate audit — lucky timing, not process working as intended.
Also worth being honest about the npm decision: burned time renaming
`@minizalo/*` → unscoped, adding `files`/`prepublishOnly`/shebang, all in service
of `npm publish`, then the user pivoted to "no npm account, tarball only" *after*
that work was done. Not wasted — the package.json publish metadata (files: [dist],
prepublishOnly build) still make `npm pack` produce a correct tarball — but the
scope rename churn for an npm registry publish that never happened is worth
naming plainly.

## Technical Details

- Bug: `parseInput` for `PUT /scenarios/:id` coerced a missing `ten` to `''`.
  Repo `update()` does `input.ten ?? cur.ten` — `''` is not nullish, so it always
  won, wiping the title on any update that didn't explicitly resend `ten`.
- Fix: made `ScenarioInput.ten` optional, `parseInput` leaves it `undefined` when
  omitted, `create()` uses `input.ten ?? ''` (only place a default is appropriate).
  Added a regression test asserting partial update preserves `ten`/`danhMuc`/`cachLam`.
- Test suite: 25/25 (16 core + 9 cli), up from 23/23 in v0.1.0.
- CI: `cli-tarball` job runs after the 3-OS release matrix — `npm pack` on both
  `minizalo-cli` and `minizalo-core`, uploads both a versioned
  (`minizalo-cli-0.2.0.tgz`) and stable-named (`minizalo-cli.tgz`) asset via `gh`
  so `releases/latest/download/minizalo-cli.tgz` is a durable install URL.
- Release assets: `MiniZalo-Setup-0.2.0.exe`, `MiniZalo-0.2.0-arm64.dmg`,
  `MiniZalo-0.2.0.AppImage`, `minizalo_0.2.0_amd64.deb`, `minizalo-cli(.tgz +
  -0.2.0.tgz)`, `minizalo-core(.tgz + -0.2.0.tgz)`, `latest*.yml`.
- Install command shipped to users: `npm i -g
  https://github.com/vuongnguyenbinh/minizalo/releases/latest/download/minizalo-cli.tgz`
  (needs Node only, no npm login).

## What We Tried

Original plan was full npm publish under `@minizalo/*` scope — discovered mid-session
the scope had never been created (404s on both packages). User chose unscoped names
instead of registering the scope. That still assumed `npm publish` as the distribution
path; user then decided against creating/using an npm account at all, so distribution
pivoted a second time to GitHub Release tarball. Both pivots landed the same session,
no wasted release — but two direction changes on distribution strategy in one sitting.

## Root Cause Analysis

Scenario bug: classic "empty string is falsy but not nullish" trap in a partial-update
handler — `parseInput` was written for the create path's semantics (always want a
`ten`) and reused unchanged for update without checking whether omitted-vs-empty
mattered for `??` semantics downstream. Distribution churn: npm scope/publish was
assumed as the plan without first confirming the user wanted to own an npm account —
should have asked "do you want to publish to npm at all" before doing the scope
rename work.

## Lessons Learned

- Any `input.field ?? current.field` merge pattern in a repo/update layer requires
  the parser to distinguish "field omitted" (undefined) from "field cleared"
  (empty string/null) — coercing omitted fields to `''` silently breaks every
  partial update. Audit every PUT/PATCH parseInput against its repo's merge logic,
  not just its create-path logic.
- GitHub Release tarball + `npm pack` is a legitimate npm-CLI distribution channel
  that needs zero npm account/scope — `files: [dist]` + `prepublishOnly` in
  package.json produce a correct tarball for `npm pack` even without ever running
  `npm publish`. Give a stable unversioned asset name so `releases/latest/download/`
  is a durable URL.
- Confirm the distribution target (npm registry vs. GitHub Release vs. from-source)
  before doing package-identity work (scope, naming) for it — this session did the
  scope rename before the "are we even publishing to npm" question was settled.
